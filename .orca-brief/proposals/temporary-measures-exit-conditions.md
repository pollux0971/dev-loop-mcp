# 候選:暫時措施要有退場條件(含「自救設定」的正式地位)

來源:專案 A(`llm_learning-cards`)技術顧問,2026-09-12。**尚未批准,素材。**

## 為什麼建議升類

按 P-78 的邏輯(同型第三次即升類),這條**已經超標**——同一天在**四個不同載體**上各撞一次:

| 載體 | 實例 |
|---|---|
| **逾時放寬** | 專案 A 的 30s,原本沒有退場條件 → 補上「等某張工單做完、重量,p95 < 2s 就收到 10s」 |
| **狀態宣稱(TODO)** | 三句「這一組現在是紅的」,實作早就在位、測試 82/82 綠;下一個人會把**真紅讀成已知待辦** |
| **暫時放寬 / 已知缺陷** | 基準與登記表那一整類 |
| **自救設定(workaround config)** | 專案 A 為了繞過 P-90 加的 `skipDirs`;**不撤的話現在無害、以後有毒** |

## 通則

> **任何「因為現在如此,所以暫時這樣」的東西都要寫退場條件,而且退場條件要是一個
> 可查的事實**(某版修好、某張工單做完、某個數字達標),不是「等有空」。
>
> **沒有退場條件的暫時措施,壽命會超過它描述的那個「現在」。**

## 「自救設定」值得單獨寫一句

它的毒性形狀特別:**它會變成沉默的分歧點——上游哪天改變主意,consumer 永遠不會知道,
因為本地覆蓋把差異蓋掉了。**

但它的**退場條件天然存在且可查**(「上游哪一版修好」),所以沒理由不寫。寫法就一行:

```json
"skipDirs": [".stryker-tmp"]   // 自救:模板 <=1.6.1 漏了它;升到 1.6.2 後撤掉
```

### 這讓「自救設定」在模板裡有了正式地位

consumer 遇到上游 bug 時本來就**該能自救,不該等上游**。把它寫成一條有紀律的路徑
(**允許自救,但要求標註上游條件**),比「請回報上游、不要自己改」實際——
**後者在上游沒修之前會逼人偷偷改**。

## 跟 #8 的關係(建議在文件裡相鄰,互相指)

| | 擋什麼 | 性質 |
|---|---|---|
| **#8**(絕對句) | 把**當時的狀態**寫成**永久的性質** | 認知問題,在**文字**裡 |
| **本條** | 把**暫時的措施**留成**永久的設定** | 行為問題,在**設定**裡 |

**同一個時間軸上的兩種腐爛。**

## 附:#8 的第四個實例(壓軸,建議收)

P-90 的那支腳本,註解寫明 `.stryker-tmp` 是「**它專屬**」的排除項,根據是
「歷史上只有我排除」——**用觀察到的分布去推斷應然的歸屬**。

這個實例特別值得當壓軸,因為**它有記錄、有理由、看起來很負責**:
前三個實例(export 無效、機器負載、ListAgents 快照)都是**沒查就寫**;
**這一個是查了、查對了、但推論方向錯了**。

「目前只有我用」跟「這是我專屬的」之間,差一個沒人問的問題:**還有誰應該用但沒用?**

> 它示範了那個病灶**不靠「偷懶」也能發作**——光是把現況當性質就夠了,
> 而**現況查得愈仔細,結論看起來愈可靠**。
