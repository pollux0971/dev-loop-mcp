# contracts/ — 跨模組約定

平行開發的支點。多個功能要能同時開工,唯一的障礙是「A 需要 B 的型別才能動」。
把這些抽出來先定案,障礙就消失了。

## 兩層,鬆緊不同

把整份契約都凍死是常見的第一個錯誤——那太重。TypeScript(或你用的語言)的型別改了
編譯器會告訴你哪裡壞,不需要走 ADR 這種儀式。分兩層:

### 硬約定(改動需要 ADR)

判準一句話:**碰到磁碟或線路的就是硬。** 檔案格式、存檔、fixture 裡寫的字、跨程序的 JSON(harness / CLI 的輸出)、
出現在 gherkin 裡的枚舉值——改一個名字會讓存檔、fixture、測試三邊同時壞的,都是硬約定。
只在記憶體裡、改了跑測試就能確認沒壞的(函式簽章、內部介面),才是軟約定。

**磁碟上的東西**,因為模組之間實際上是靠檔案溝通的,而且改了會讓已產生的資料失效。
把你的硬約定章節列在這裡,例如:

| 章節 | 內容 |
|---|---|
| {{HARD_SECTION_1}} | (範例:核心實體的檔案格式與必填欄位) |
| {{HARD_SECTION_2}} | (範例:狀態檔 / 進度檔的 JSON 結構) |
| {{HARD_SECTION_3}} | (範例:目錄結構) |
| {{HARD_SECTION_4}} | (範例:模組間共用的任務型字串常數與路由表——如果有 LLM 或多 provider 路由) |

改這些之前先問:**能不能不改?** 多數「需要新欄位」其實是模組內部的事。

### 軟約定(改了跑測試、更新這份文件就好)

**只存在於記憶體的介面**。改了編譯器會抓、測試會抓:

| 章節 | 內容 |
|---|---|
| {{SOFT_SECTION_1}} | (範例:某個計算結果的回傳型別) |
| {{SOFT_SECTION_2}} | (範例:核心函式的輸入輸出簽章) |
| {{SOFT_SECTION_3}} | (範例:檔案系統存取的抽象介面,方便測試用記憶體實作替換) |

規矩很簡單:改的人負責跑全部測試、更新這份文件、在 commit 訊息說一句為什麼。
不用 ADR,不用等確認,不用列重驗清單。

## 為什麼還是需要契約

如果團隊很小(一個人加一個 AI 配對開發者),契約的價值不在「治理」。它在兩件事:

1. **你可以挑任何一個資料夾開始而不被卡住**
2. **AI 在不同 session 之間不會偷偷漂移** — 這個更重要。沒有契約,今天寫的某個型別
   和下週寫的同一個型別會長得不一樣,而且要到整合時才發現

## 內容

| 檔案 | 內容 |
|---|---|
| `types.md` | 型別與檔案格式,標明硬 / 軟 |
| `fixtures/` | **真的測試資料檔案**,不是規範。直接拿來用 |

`types.md` 是規格,建議由某個 Wave 0 的能力(例如你的資料層 / schema 層)把它變成
可執行的驗證(zod schema 或等價物)。在那之前其他功能照著手寫自己需要的型別,
整合時換掉。這個短暫的重複是平行的代價。
