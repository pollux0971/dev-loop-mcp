# Explain:把程式講清楚

改寫自 pstack 的 how、teach、bro(MIT,見 `docs/dlm/THIRD-PARTY.md`)。

目標:使用者聽完能自己判斷「要不要改、改哪裡」。不是逐行註解。

## 步驟

1. 先說你理解的問題範圍(一句)。範圍不清楚就照最可能的讀法做,使用者可以改。
2. 判斷大小:
   - 小(一個檔、一個函式、一個指令):自己讀完直接講。
   - 大(跨好幾個模組、整個資料流):用 Agent 工具開 2–4 個唯讀 subagent,每個負責一個切面
     (例:進入點與指令、資料模型與儲存、外部依賴與設定)。每個回報:相關檔案:行、它看到的流程、看不懂的地方。
     收齊後你自己對照程式,解決它們互相矛盾的地方。沒有 Agent 工具就自己依序讀。
3. 有 dlm 的紀錄就一起看:`node tools/dlm.mjs show <節點>` 看這個節點的 intent、owns、gherkin;
   `docs/AS-IS.md`、`docs/ROADMAP.md` 是現況與方向。說明以程式為準,文件跟程式不一樣時講出來。
4. 照下面的格式講,用不到的段落省略。

## 格式

- **一句話**:這東西是什麼、為什麼存在。
- **怎麼運作**:從觸發點一步一步走到結果,講清楚資料從哪裡來、存到哪裡、從哪裡出去。
  三個以上元件互相呼叫時畫一張 mermaid 圖(最多 6 個方塊)。
- **東西在哪**:要動手時要看的檔案,一行一個,附 `檔案:行`。
- **要小心的地方**:沒有測試保護的地方、改一處會連帶壞的地方、看起來像 bug 但可能有人依賴的行為。

## 寫法

- 白話、完整句子。講「`ledger.mjs` 的 `append()` 先拿鎖再寫一行」,不講「帳本模組負責持久化」。
- 每個說法附 `檔案:行`,或標「推測」。讀不懂就寫「不確定:…」,不要補一個合理的答案。
- 使用者說「講簡單一點」:拿掉檔名與術語,用一般人的話重講一次,意思不變。
- 這個 skill 只讀。使用者聽完要改東西,回到 front 的「使用者要新東西」。
