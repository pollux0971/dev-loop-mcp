# fixtures/ — 真的測試資料

不是規範,是可以直接讀取的檔案。每個功能單獨跑的時候吃這裡的東西,
所以整合時大家對「某筆固定的測試資料長什麼樣」的理解一致。

## 清單(依你的專案調整資料夾名稱)

```
{{FIXTURE_MINIMAL_DIR}}/     一個合法的最小資料集,{{FIXTURE_MINIMAL_DESC}}。驗證器應該回報 0 個問題
{{FIXTURE_BROKEN_DIR}}/      刻意壞掉的,附 EXPECTED.md 列出每一個問題
{{FIXTURE_UNIT_DIR}}/        單一實體的合法與非法樣本,檔名說明錯在哪
{{FIXTURE_STATE_DIR}}/       各種狀態組合(例如排程/進度的邊界案例)
{{FIXTURE_EXTERNAL_DIR}}/    需要重播的外部呼叫紀錄(如果有 LLM 或第三方 API)
{{FIXTURE_RAW_DIR}}/         原始輸入素材樣本
```

沒有用到的種類就刪掉那一行;需要更多種類就照這個格式加。

## 規則

- fixture 是硬約定的一部分。**加新的隨時可以;改既有的要 ADR**,因為別人的測試靠它
- 每個 invalid fixture 的檔名要說明錯在哪
- 每個 `EXPECTED.md` 是對應驗證器的答案卷:每個問題一行。驗證器找到的數量必須相符
- 需要重播的外部呼叫記錄,檔名格式用 `<task>.<情境>.json` 這類可以被程式確定性選取的規則

## 還缺的

先做出最小可用的一套即可。以下等你手上有真資料時再補,不必現在造:

- 一份「豐富版」fixture(多類別、多層次、含各種標記)。**建議做法:第一次整合通過後,
  拿你真的餵進去的東西挑一份出來當 fixture**,比人造的好用
- 更多外部呼叫重播——同上,第一次整合之後把真的回應存下來
