# Interrogate:批准之前先挑毛病

改寫自 pstack 的 interrogate(MIT,見 `docs/dlm/THIRD-PARTY.md`)。好處來自「審查者彼此獨立」:兩個都抓到的問題最值得看。

## 1. 範圍

- **提案**(最常用):`.dlm/intake/` 的 bundle 與 gherkin,或 `node tools/dlm.mjs show <提案id>`。
- **已合併的一版**:上一個整合點到現在的 `git diff`(`git log --oneline` 找 `dlm-archive/` 標籤),加這一版的 gherkin。
- 使用者指定的檔案或節點。

## 2. 意圖

用一段話寫出這個提案或這一版要做到什麼(從使用者原話、bundle 的 goal、ROADMAP)。寫不出來就先問使用者。

## 3. 開審查者

用 Agent 工具在同一則訊息開兩個唯讀 subagent,給一樣的材料與意圖,不給彼此的結果。
能換模型就換(例:一個用 opus、一個用 sonnet);這台電腦有登入的 Codex 帳號(`dlm account list`)也可以讓其中一個用
`codex exec` 跑。沒有 Agent 工具就自己依序做兩次,第二次刻意從相反的角度看。

每個審查者照這些角度找問題,每條附 `檔案:行` 或 gherkin 的場景名:

- **規格算得對嗎**:每個場景裡的數字逐一驗算(總和、餘額、日期區間、排序、四捨五入)。
- **漏了什麼**:錯誤輸入、空資料、邊界值、重複執行;使用者說過要但沒有場景的事。
- **切得對嗎**:節點的 owns 有沒有重疊或漏掉要改的檔;依賴順序;兩個節點要共用的格式有沒有契約。
- **整合點試得出來嗎**:@e2e 場景是不是使用者真的會做的操作,做完看得到結果。
- **已合併的程式**:是不是只對測試值寫死、錯誤被吞掉、檢查散在中間而不是在入口、測試只驗內部呼叫而不是行為。

## 4. 合併與判斷

同一個問題講法不同就合併,記下哪些審查者提到。你是主審,不是統計員,把每條分到一格:

- **要改**:會讓這一版做錯、做不出來,或使用者試用一定會發現的問題。
- **可以考慮**:合理,但改的代價不一定值得。
- **備註**:對,但現在不用處理。
- **駁回**:錯的、吹毛求疵、或缺了背景,附一句理由。

## 5. 回覆

1. 意圖(一段)。
2. 審查者:誰、用什麼模型、各提幾條。
3. 要改 / 可以考慮 / 備註 / 駁回,每條一兩句,寫哪些審查者提到。
4. 一致與分歧:兩邊都抓到的是什麼,只有一邊抓到的是什麼。

最後問使用者要怎麼處理「要改」的那幾條。改提案就照 `intake` 重寫並 `--supersedes` 舊提案;
已合併的問題就提一個新節點。使用者沒說好之前,什麼都不改、不 decide。
