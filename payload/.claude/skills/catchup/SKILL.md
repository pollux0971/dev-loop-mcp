# Catchup:你不在時發生了什麼

改寫自 pstack 的 ketchup、recall(MIT,見 `docs/dlm/THIRD-PARTY.md`)。

這一輪只讀:不決定、不合併、不啟動或停止任何東西。

## 收集

1. 範圍:預設是使用者上次說話之後;他講了「這週」「昨天」就用他的。先說你用的範圍。
2. 有 MCP 工具時:`dlm_overview` 看所有專案,每個有事的專案再 `dlm_get_inbox`。
   沒有時:`node tools/dlm.mjs status`、`node tools/dlm.mjs inbox --no-mark`(不要把「上次看之後」標成看過,
   除非使用者看完了)。
3. 每件要決定的事用 `node tools/dlm.mjs show <ref>` 拿到選項、建議與理由。
4. 數字(合併幾個、花了多少)從指令輸出抄,不要估。

## 回覆的順序

1. **第一句**:有幾件事等他,或沒有事等他。
2. **發生了什麼**:每個專案一到三行白話。講對使用者有什麼不同(「記帳的匯出可以用了」),
   不講 dispatch id、分支、指令。有一串節點時畫一張 mermaid 圖:節點、依賴、狀態(最多 6 個方塊)。
   中途壞掉又修好的事講一句。
3. **等你的事**:每件一個項目,讀完這段就能回答,不用再問:
   - 要他決定什麼,dlm 的建議是什麼,為什麼;
   - 選了會怎樣、不選會怎樣;風險就算低也寫一句(例:「低風險:只改了文案」);
   - 整合點要試用的:怎麼跑、看什麼算成功。
   好幾件是同一種決定(例:五個待合併)就寫一次問題與建議,每件一行。
4. **我還能自己做的**:一行(例:「要的話我可以開主控台給你看」)。

## 不要

- 不把還在等他的事說成做完了。
- 不補一件他不需要決定的事來湊數。
- 不把 worker 或模型寫的字講成事實:說「worker 說……」。
- 他回答之後,照 front 的「使用者回答待決事項」做。
