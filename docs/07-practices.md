# 採用專案驗證過的做法

三個專案共用同一套範式:A(本 repo,greenfield)、B(AI_KM,272 張 story 的企業平台,brownfield)、
C(nightmare-assault,823 張 story 的遊戲,brownfield)。這份文件收 B、C 在採用之後自己補出來、
回報「這個值得進範式本體」的做法,以及 A 協調者自己在派工與審核中發明、範式原本沒寫的做法——
不是口號,每條要有做法、為什麼、證據(實際數字或事故)、怎麼落地。**不是每條都驗證過**;
沒驗證過的標【推】。

判準跟 `PITFALLS.md` 一樣:換一個專案還會需要才收;專案專屬的細節不收。

## (a) 每個量尺附陽性對照

**做法**:任何負責「守門」的量尺——見證器、marker gate、`grep FAILED` 計數、standalone 檢查——
旁邊都要放一個**故意壞掉的樣本**,而且要求「這個樣本必須被讀到」。沒有陽性對照的量尺不算 gate,
只是一個看起來像 gate 的數字。

**為什麼**:量尺可以在完全不報錯的情況下讀到錯的東西,而且錯法通常是「恆定值」或「巧合對上」,
沒有比較基準看不出來——這叫觀測塌縮:量尺看起來正常運作,實際上沒在量。

**證據**:C 一天內抓到三次獨立的觀測塌縮:見證器拿錯檔案,分數恆為 0(從沒真的量過);
`grep FAILED` 把不相關的字串多算進去,結果多算 5;兩個各自宣稱「單一事實來源」的計數
其實在暗中互相校正,撞出同一個數字讓人誤以為互相驗證。三次都是**加了故意壞掉的陽性樣本
之後才現形**,加之前分數看起來完全正常。

**怎麼落地**:
- 見證器類:放一個刻意標記為「應該被抓到」的退化案例,量尺跑完後必須把它列進報告,沒列到就是量尺本身壞了。
- marker / grep 計數類:在被掃描的語料裡放一行明知道會被算進去的假陽性字串,計數跟預期不符就是掃描邏輯錯了。
- standalone / 執行檢查類:見 `check-doc-links.ts` 已經採用的模式——「掃到 0 條」跟「全部通過」退出碼一樣是 0,
  所以掃到 0 個目標一律 FAIL(這條規則本專案 A 已經在多支守門腳本裡用,C 把它抽象成通則)。
- 落地時機:量尺**上線那天**就要有陽性對照,不是「之後有空再補」——三次事故都是量尺已經跑了一段時間、
  大家已經信任它之後才發現。

**刻意不遵守的專案**:無。三個專案都採用,B 的反向建議是「機制要量不要讀」這句話對範式作者
自己也成立——本模板出版前如果沒有機械比對(`verify-against.sh`),同樣是一個沒有陽性對照的宣稱。

**修正(來源 nightmare-assault,2026-09-05,見 PITFALLS P-68)**:陽性對照容易被做成只驗「被測物
存在」,不是驗「探針本身有作用」——四個實測到的例子:反向驗證以為新程式碼被執行到但其實沒有;
一個探針送出去的其實是另一個動作(`propose_map_action` 送的是 `inspect`);貪心式探針在交替情境下
互相誤判;grep 抓的輸出格式跟實際輸出格式早就不一樣,六個能力全報 0 沒人發現。放陽性對照樣本時,
除了「壞掉的東西必須被讀到」,還要多驗一次「探針拿去一個已知非 0 的情境跑,真的量得出東西」——
兩者缺一都不算完整的陽性對照。

## (b) 端到端 harness 走到第幾階的棘輪基準檔

**做法**:黃金路徑(golden path,系統從頭到尾真的能跑完一次的那條路)配一個「假玩家 / 假使用者」
harness,結果寫進一份 committed 的棘輪基準檔(例:`agent_play_baseline.json`),記錄「這次跑到第幾階」。
規則是**單向棘輪**:這次跑到的階數比基準低 → 紅(退步);比基準高 → 也要紅,強迫把基準檔撥高
(不撥高,下次退步不會被抓到)。黃金路徑本身**不准有測試側後門**——不能為了讓 harness 跑得過去
而在生產路徑裡塞一個只有測試會用到的分支;產生結果的入口(oracle)只准一個,harness 跟正式
使用者路徑必須是同一個函式呼叫。

**為什麼**:端到端 harness 最容易被「悄悄改鬆」——退步時沒人注意(反正基準檔沒變,對比不出來),
進步時也沒人記錄(基準檔沒跟著漲,實際上進步的空間被浪費,也代表沒有人真的在盯這個數字)。
測試側後門則是另一種塌縮:harness 綠了,但走的是正式使用者永遠不會走的路徑。

**證據**:C 用這個機制當 DoD(Definition of Done)的核心項:一個 phase 沒有讓 harness 的階數
往前推進,不算做完;`reached>base` 也強制紅,是為了不讓「這次進步了但沒人記錄」變成常態。

**怎麼落地**:
1. harness 跑一次黃金路徑,產出「走到第幾階」的整數或列舉值。
2. 基準檔 committed 進 repo,格式簡單到一行 diff 看得出漲跌。
3. CI / 完整檢查裡加一個比對步驟:`reached != baseline` 一律非 0 退出碼,訊息區分「退步」與「該撥高基準」。
4. 撥高基準是**獨立 commit**,訊息寫清楚為什麼進步了(哪個 phase 讓它往前);不要跟功能改動混在同一個 commit。
5. 審核清單加一條:「這個 phase 交付的東西,黃金路徑走的是不是它加的那個分支」——防止 harness 測著一條
   只有 harness 自己會走的路。

**刻意不遵守的專案**:A 尚未實戰(還沒有假玩家 harness 這類 e2e 場景需要它);B 沒有單一線性的
「黃金路徑」概念(企業平台的完整流程分岔多),改用 `@e2e` 場景清單當等價物,棘輪換成「场景數
只能增不能減」。

## (c) 收斂指標只看兩個數:只升 / 只降

**做法**:專案有沒有在收斂,只看兩個數:黃金路徑走到第幾階(只升,見 (b)),與見證器裡
「未標記為允許退化」的測試數(只降,見 (f))。**todo / 工單數量不算收斂指標**——它會被新開的
工單稀釋,永遠不會真的趨近於零。

**為什麼**:todo 數是一個會同時被兩股力量推動的數字(修掉一個、新開一個),看不出淨方向;
真正代表「系統變得更可信」的是「能做到的事變多」與「沒人管的退化路徑變少」,這兩個是單調的。

**證據**:C 用這兩個數字取代原本的 story 完成度百分比,一天之內看得出「假玩家進度停滯但退化
測試數在降」這種原本會被完成度百分比蓋過去的訊號。

**怎麼落地**:
- 每輪 / 每個 sprint 回報只列這兩個數字的變化(現在多少、上次多少),不列 todo 剩幅或百分比進度。
- 兩個數字任一方向錯了(該升沒升、該降沒降)都要能講出原因,講不出來就是有東西被漏掉。
- 工單清單依然要維護(見 (i)),只是不拿它的長度當進度指標。

**刻意不遵守的專案**:A、B 沒有「見證器未標記數」這個現成的量(還沒有退化見證器機制,見 (f)
的落地程度),暫時只用黃金路徑 / `@e2e` 场景數這一個指標,todo 數仍列在 sprint 檔裡但明確標
「不是進度」。

## (d) 「沒有指令的數字不算數字」

**做法**:任何交接文件、checklist、`.orca-brief/REVIEW.md` 裡出現的量化數字,旁邊要附**產生這個數字的實際指令**
與**取數的日期戳**。審核 / 交接時重跑那條指令,對不上就代表前提已經過期,不能沿用。

**為什麼**:main 每小時都在動,沒有指令的數字本質上是「某人某個時間點看到的東西」,傳到下一個人
手上時已經失去可驗證性——傳話的人如果連自己怎麼算出來的都講不清楚,收訊的人更不可能發現它過期了。

**證據**:C 的交接文件一天內出現三處前提過期的數字(工單數、通過的場景數、覆蓋率),
全部是「寫的時候對,交接時已經不對」;本模板自己也在 PITFALLS P-15 記過同一件事——
ADR / REVIEW 裡一個量化數字(72 對 / 34 對)審核輪重跑後其實是 75 / 33,審核輪原本會照抄舊數字。

**怎麼落地**:
- 交接文件的每個數字格式:`<數字>(`<取數指令>`,取自 <日期戳>)`。
- 審核 / 驗收時,任何要引用的數字先重跑一次指令,不信任何轉述的數字,即使轉述的人是自己上一輪的自己。
- checklist 類文件如果數字會隨時間變(檔案數、覆蓋率),優先用「跑這條指令,結果應該長這樣」取代寫死的數字。

**刻意不遵守的專案**:無;三個專案都採用,只是 A 目前只在 PITFALLS P-15 的框架下套用到「量化數字」,
還沒有像 C 一樣把它變成交接文件的固定格式要求。

**量退出碼時不接 pipe**:`cmd | tail` 這種寫法,`$?` 抓到的是 `tail` 的退出碼,不是 `cmd` 的——
`cmd` 本身可能已經非 0 退出,但 pipeline 的退出碼只看最後一個指令,`tail` 幾乎永遠是 0。要量
`cmd` 的退出碼,先把輸出存進變數再看 `$?`:`out=$(cmd); rc=$?`,需要的話再用 `echo "$out" | tail`
單獨看要看的那幾行。技術顧問曾經因為這樣差點回報一個假的 exit 0(bash 有 `pipefail` 選項能部分緩解,
但不是所有殼層腳本都設了,不能假設對方已經開;`out=$(cmd); rc=$?` 不依賴那個選項,永遠對)。

## (e) 定向反向驗證當 gate(規格)

**做法**:把「這條測試真的守著這行程式碼」做成一個**可重複執行的 gate**,不是變異測試分數這種
統計指標。核心是逐張指定的定向突變:告訴工具改哪個檔、把什麼換成什麼、預期哪個測試 / 場景一定要
失敗(可選:失敗訊息要包含哪段文字)。跑法固定五步:

1. **基準必須先綠**:目標檢查(`--expect-fail` 指定的測試 / 場景)在突變前必須通過,不通過代表
   前提已經壞了,gate 本身要用一個獨立的退出碼中止,不能往下跑。
2. **突變**:在指定檔案裡找 `--replace` 指定的字串。找到 0 處是使用者寫錯目標,找到 >1 處而沒有
   加 `--nth` 指定第幾個命中,一律拒絕執行——多處命中時工具不猜使用者要哪一個,沒有 `--nth`
   就是設計錯誤,不是「隨便挑一個跑跑看」。
3. **必須變紅,而且紅得對**:突變後重跑目標檢查,必須失敗;而且失敗必須是**斷言失敗**(能定位到
   具體哪個判斷不成立),不能是語法錯誤、例外、逾時這類「程式碼壞了但不是規格失敗」的紅——
   後者代表這條反向驗證量錯了東西,要分開歸類,不能算過。給了 `--expect-message` 時,失敗訊息
   要包含那段文字,不是「有紅就算」。
4. **精確還原**:用 `git show HEAD:<path>` 讀回原內容寫回去,或寫進 worktree 專屬的暫存目錄
   (**不要**用 `git checkout -- <file>`,會連同同一檔案裡其他未 commit 的合法編輯一起清掉;
   也**不要**寫進 `/tmp` 共用目錄,平行 session 會互相覆蓋),寫回後用 `sha256sum` 逐位元比對,
   證明真的回到原狀,不是「看起來一樣」。
5. **exit code 分類,不是布林值**:至少要分得出——基準本身沒過(中止)、目標字串找不到、多處命中
   未給 `--nth`、突變後仍然通過(代表這是一個假陰性,gate 存在的理由就是抓這個)、突變後失敗但
   不是斷言失敗(分類錯誤,不算過)、突變後失敗且是預期的斷言失敗(通過)。每種對應一個固定的
   退出碼,呼叫端(CI、審核腳本)照退出碼分流,不解析文字。

**證據作為決定性依據**:通過的證據是**炸掉那條斷言的失敗訊息原文**,不是「紅了幾條」——同一個
場景可能有多條斷言,只有第一條炸的斷言決定這次驗證抓到了什麼;紅的**條數**不能取代訊息本身
成為證據(見 (h))。

**工具要自帶 meta-test**:工具本身要有一組已知答案的合成樣本(明知道該被抓到 / 明知道該被放過),
驗證工具自己判斷「假陰性 / 誤判 / 正確分類」的邏輯沒有腐化——工具是 gate 的 gate,不能只靠人工複查。

**證據(來源專案)**:C 的 `mutate.py` 用這個機制跑過 121 張定向反向驗證,抓到一次 `.pyc` 快取造成
的假陰性(改了 `.py` 原始碼,測試讀的是舊的編譯快取,分數看起來正常但完全沒測到新程式碼)。
B 的 `mutate.mjs` 走同樣的核心邏輯,退出碼用 `exit 5` 代表「突變沒有讓測試變紅」這個最關鍵的分類,
並且是 DoD 明文要求的形式:「這條場景對這行程式碼一定要紅」。

**狀態**:這是規格,不是全部已經收進本模板的實作。**TS 版待做**——本模板的工具鏈是 TypeScript,
應該以 `scripts/mutate.ts` 的形式落地,介面比照上面的 CLI 形狀(`--file --replace --with
--expect-fail [--expect-message] [--nth]`)。**Python 版**(C 的 `mutate.py`)已有實戰驗證,
**已收於 `scripts/py/mutate.py`**(連同 meta-test `scripts/py/test_mutate.py`,模板 1.3.1,
使用者授權;用法見 `scripts/py/README.md`)——多處命中拒絕與 `--nth` 是專案 C 原本就有的
實作(STORY-70-14),`--expect-message` 目前 Python 版尚未支援。

**跟變異測試分數的關係**:見文末「三個專案都刻意不遵守的範式條文」——嚴格級門檻現在變異分數與
定向反向驗證二選一都算數。

**刻意不遵守的專案**:A 尚未實作對應腳本(這正是本節列為「待做」的原因)。

## (f) 退化見證器

**做法**:測試框架的固定掛勾(例如 pytest 的 `conftest.py`,或對應框架的全域 setup/teardown)
記錄**每個測試實際走了哪條分支**——是正常路徑,還是某種 fallback / 預設值 / mock 頂替。
見證器有兩段:先跑「報告模式」列出所有走過 fallback 的測試清單,**再**執法(把清單裡沒有明確
標記 `allow_degraded` 的一律判紅)。順序刻意分兩段,不是一次到位——直接執法會在還沒盤點清楚
的情況下炸掉一大片,先出清單讓人判斷哪些是刻意允許的退化、哪些不是,再收緊。

**為什麼**:綠燈只代表斷言成立,不代表**測到了想測的東西**。一個測試可能走進 fallback 分支之後
斷言仍然成立(兩邊都退化成同一個預設值,所以「相等」),測試本身沒有說謊,但它驗證的已經不是
規格要的行為——這跟 PITFALLS P-13「`@manual` 場景人親手確認了,功能還是壞的」是同一個病灶:
人或測試看到的是退化路徑上的畫面。

**證據**:C 在導入見證器後,一天內抓到七個這類假綠;其中 35 個測試檔在 fallback 上綠了很久,
沒有見證器之前完全沒被發現——它們的斷言邏輯都沒錯,錯的是走到那條斷言之前的路徑。

**怎麼落地**:
1. 全域測試掛勾裡放一個記錄點:每次測試執行時,把「走了哪個實作分支」(正常 / fallback / mock)
   記進一份報告檔(不進斷言,只記錄)。
2. 先用報告模式跑一輪,列出所有落在 fallback 分支的測試,人工過一輪,對「刻意允許退化」的
   測試加上 `allow_degraded` 標記(寫在測試本身或設定檔)。
3. 切到執法模式:落在 fallback 且沒有 `allow_degraded` 標記的測試一律判紅。
4. `@manual` / `@e2e` 這類需要人眼確認的場景,**先看見證器報告再確認**——退化路徑上的綠燈與
   人工確認都不算數。

**刻意不遵守的專案**:A、B 尚未實作對應的掛勾機制(A 目前只有 P-13 這條踩坑紀錄,還沒有見證器
本身);兩者暫時靠審核清單裡的人工檢查頂著,是已知的較弱替代品。

## (g) 審核拿掉對照表宣稱的守門重跑,嚴格級另開 session

**做法**:嚴格級模組的審核不是「讀審核報告」,而是拿對照表(突變 / 場景 / 反向驗證清單)裡
**每一列宣稱擋住的東西**,重跑一次驗證真的擋得住——不是重跑整份測試看綠燈,是刻意驗證
「如果這個東西沒被擋住,現在應該紅」這件事本身成立。而且這個審核必須在**另一個 session**跑,
不能是宣稱通過的同一個 session 順手看一眼。

**為什麼**:「宣稱通過」跟「真的擋得住」是兩件事,前者可能只是讀了自己寫的報告產生的錯覺;
同一個 session 覆核自己剛做的事,盲點跟做的時候一樣。

**證據**:B 兩天內抓到 4 次「綠但沒證明」——測試全過、變異分數達標,但對照表宣稱擋住的具體
行為,重新驗證後發現根本沒被任何斷言真正涵蓋(跟 PITFALLS P-29「開發 agent 自主判斷沒有測試
保護」是同一類問題的審核端版本)。

**怎麼落地**:
- `/phase-done` 的變異測試步驟(第六步)在對照表存在時,加一條:「對照表每一列,拿掉它宣稱
  的守門重跑一次,場景必須紅」——這已經寫進本模板的 `phase-acceptance` skill。
- 嚴格級的驗收固定由另一個 session 跑,不是同一個開發 / 審核 session 自己蓋章。

**刻意不遵守的專案**:C 用定向反向驗證(見 (e))取代「對照表重跑」這個人工動作——工具本身
就是那個「拿掉宣稱的守門重跑」的機制,所以不需要額外一個 session 手動做同樣的事;但**嚴格級
仍然要求另一個 session 審**,只是審的對象換成工具跑出來的分類結果而不是人工重跑。

## (h) 反向驗證證據是失敗訊息原文,紅的條數不算

**做法**:反向驗證(見 (e))通過的證據,是**炸掉那條斷言時,失敗訊息的原文**,貼進報告或
commit body。**不是**「幾條測試變紅了」這種計數——計數可以被巧合湊出來(例如同時炸了三個
不相關的斷言),原文能證明「真的是規格要的那個判斷不成立了」。

**為什麼**:數字是聚合過的資訊,會抹掉「到底是哪個判斷失敗」這個關鍵細節;失敗訊息原文是
一次性、無法偽造的證據——你不可能貼出一段「因為 X 不等於 Y」的訊息卻沒有真的讓 X 不等於 Y。

**證據**:B 的 `mutate.mjs` 用 `exit 5` 搭配 `--expect-message` 把這件事變成機器可驗證的規則,
而不是靠人眼看報告有沒有貼原文;導入前的審核只看「紅了幾條」,曾經被一次巧合命中的無關失敗
騙過。

**怎麼落地**:
- commit / `.orca-brief/REVIEW.md` 裡任何反向驗證的段落,格式固定為「改壞了什麼 → 失敗訊息原文(逐字貼)→
  還原證明(sha256 前後)→ 回綠證明」,不接受「N 條測試從綠變紅」這種摘要當唯一證據。
- 同一場景多條斷言時,**第一條炸的斷言**決定這次驗證的意義——後面連鎖失敗的斷言不需要逐一列出。
- 斷言要對著「壞掉時真的會變的量」寫(分數、順序、內容、身分),不能是「有結果」「長度 > 0」
  「沒拋錯」這種存在性斷言——這類斷言在東西壞掉之後往往仍然成立。

**刻意不遵守的專案**:無。

## (i) 工單清單一律從 grep 推導

**做法**:任何「這批要處理的清單」(工單、待改檔案、待補測試),接手的人**自己重新 grep 一遍**
確認範圍,不信任何人列出來的清單——包括寫工單的人自己列的清單。工單裡明講：「我列的清單可能
不完整,發現漏掉的列進回報,不要默默補也不要默默跳過」。

**為什麼**:列舉是人工動作,人工動作會漏;而且列清單的人跟改清單的人如果是同一個人,漏掉的
地方通常兩邊都漏——列舉本身不是獨立於執行的驗證。批次字串替換也是同一族問題:`sed` / `replace`
找不到目標時**不報錯**,安靜回傳原字串,「沒有壞消息」被當成「好消息」。

**證據**:B 用這個規則抓到「自己 grep 標 1 處,實際 2 處」的落差——出工單的人自己覆核都會漏。

**怎麼落地**:工單模板(見 `.orca-brief/TASK.md.template`)固定一節「不要從我的列舉推導範圍——
自己 grep」,附需要窮舉的目標(例如某個字串在全 repo 的出現次數、某個函式的呼叫點);
批次修改類操作接一個「因為沒改到而失敗」的檢查(`assert old in s` 再 replace,或改完 grep
舊字串應為 0 命中),把檢查輸出貼進紀錄——這條同時也是 PITFALLS P-40 的防線。

工單模板本身的每一段,都是「之前少寫這段就出過事」換來的,不是憑空設計的規範:

| 段落 | 沒寫它時出的事 |
|---|---|
| 第 0 件事:自報跑在哪個模型 | 沒有機制確認 worker 實際是哪個模型,派工與能力不對等發生時查不出來 |
| 「只在這個目錄工作」 | cwd 殘留到別的 worktree,檢查跑在錯的 tree 上還看起來正常(同 PITFALLS P-19) |
| 「絕對不能碰的」用路徑列舉,不寫「共用檔」三個字 | 寫「共用檔」worker 會自己判斷哪些算共用檔,判斷跟協調者的認知對不上 |
| 逐項「每條自帶驗收條件與反向驗證」 | 反向驗證統一寫在工單最後一段時,worker 只挑最好驗的那一條做,其餘悄悄跳過 |
| 「不要從我的列舉推導範圍——自己 grep」 | 出工單的人自己標的範圍(標 1 處),實際有 2 處,少的那處沒人發現 |
| 反向驗證的還原手段禁令(不用 `git checkout --`、不寫 `/tmp` 共用目錄) | 並行 session 互相覆蓋對方寫在 `/tmp` 的還原備份,還原失敗且難以追查 |
| 「被 grep/tail 濾成空的輸出 = 失敗」 | 檢查指令被過濾成空時當成「沒問題」蒙混過去(PITFALLS P-15) |
| 「完成前必跑」段落裡「哪些紅是還沒做」的提示欄 | worker 把預期內、還沒實作到的紅誤判成自己弄壞了去硬修,或反過來把真正弄壞的紅當成「本來就會紅」放過 |
| 回報格式裡的「我做的自主判斷」清單 | 開發時的自主判斷沒有測試保護也沒人知道(PITFALLS P-29),審核找不到東西可以破壞 |
| 「工單哪裡說不通」 | 工單前提本身是錯的,worker 硬照做湊出一個綠;兩次擋下模板迴歸的前提錯誤,都是 worker 在這欄回報出來的,不是協調者自己發現的 |

**刻意不遵守的專案**:無。

## (j) 顧問錯誤具名記錄

**做法**:技術顧問(或任何審核 / 判斷角色)犯的錯,**具名**登進 `PITFALLS.md`——誰、在哪一步、
原話寫什麼——不是含糊地寫「曾經有個判斷錯了」。這樣協調者下次遇到類似情況,才有足夠具體的
依據**退回**顧問的判斷,而不是預設顧問說的都對。

**為什麼**:協調者的位階通常低於顧問(顧問做設計判斷,協調者只執行),沒有具名記錄的先例,
協調者很難有底氣說「上次你也是這樣講,結果是錯的」——具名記錄把「不信任」變成有依據的、
可以引用的東西,而不是憑感覺質疑。

**證據**:PITFALLS 本身已經有多條顧問自己踩的坑具名記錄(P-15「技術顧問自己踩的」、P-19
「技術顧問自己踩的」、P-27「裁決者對沒法驗證的平台問題」、P-37「技術顧問 `git push --tags`
誤推」)——B 把這個做法明確規則化:**PITFALLS 的「來源」欄要能回答「誰、哪一步」**,不能只寫
專案名稱。

**怎麼落地**:`PITFALLS.md` 的來源欄改名「來源 / 誰 / 哪步」(見本模板 1.3.0 的改動);
新增條目時,顧問的錯誤跟開發 / 審核 agent 的錯誤同等對待,一樣具名、一樣進 PITFALLS,
不因為犯錯的是「判斷比較貴的角色」就從寬記錄。

**刻意不遵守的專案**:無。

## (k) 同型第三次即升類

**做法**:同一種型態的問題第三次出現時,**不再當個案處理**,升級成「類項目」——開一張處理
這整個類別的工單(通常是加一條 gate、改一條規則、或做一個小工具),已經發生過的個案列成這張
類項目底下的驗收清單(逐一確認新機制真的擋得住它們),而不是繼續一個一個修。

**為什麼**:前兩次可以合理當巧合或個案處理;第三次代表背後有一個結構性原因在重複產生同一種
錯誤,繼續當個案修只是在治標,而且每次修的成本不會下降。

**證據**:C 一天內同一型的問題出現了 8 次個案,升類之後收斂成兩張類項目工單。本模板自己的
PITFALLS 也已經用這個判準:P-29(自主判斷沒有測試保護)、P-33(守門對著代理指標而非不變量)
都在描述裡明講「同型第三次」。

**怎麼落地**:
1. 追蹤問題時順手記型態標籤(不需要正式分類系統,一句話描述型態即可,例如「守門用代理指標」)。
2. 同型態第三次出現時停下來問:「這個型態的下一次要怎麼被自動擋住,而不是靠人再認出來一次?」
3. 開類項目工單:內容是機制本身(gate / 規則 / 工具),附上已知的個案清單當它的驗收條件。
4. `autopilot` 的維護清單(§3)在「沒事可做」時,順手掃一遍最近的問題紀錄有沒有同型第三次
   出現,不必等人手動觸發。

**刻意不遵守的專案**:無;A 尚未實際遇到第三次同型案例,還沒有落地機會,但機制已經寫進
`autopilot` 的維護清單準備好接手。

## 來自專案 A 協調者的做法

這四條不是採用專案回報的,是本 repo(A)的協調者自己在派工與審核裡發明、範式原本沒寫的做法,
連同自己犯的錯一起記——來源標「專案 A 協調者」,格式跟上面一致。

### (l) 協調者轉述一律預設【推】

**做法**:協調者傳給 worker、使用者、或寫進工單的任何「技術顧問說的」「文件裡寫的」內容,
**預設**標記為推測【推】,不是「必要時才標」——預設值站在懷疑那邊,標【驗】只在協調者自己
親手重跑過指令、看到原始輸出的時候。

**為什麼**:協調者是整條轉述鏈裡離事實最遠、卻最常需要下指令的一環;工單一旦寫成肯定句,
worker 通常直接照做,不會回頭懷疑。而且協調者自己往往是「把別人講的或文件寫的當事實傳下去」
這個錯誤犯得最多的角色——不是因為粗心比較多,是因為轉述本來就是協調者的日常工作內容。

**證據**:PITFALLS P-38 記錄的模板同步迴歸,兩次觸發語句都是協調者寫的「行為相同,只多 ROOT」
「我跑過,跟 main 一模一樣」,兩次都是假的;第二次協調者學乖標了【推】,worker 才沒有直接
同步過去,第一次沒標,是 worker 自己實測才擋下來的,不是協調者的功勞。同一次自省還列出協調者
自己另外兩個編造數字的例子(工單裡寫了兩個從 REVIEW 舉例段落抄來、但沒查證的基準數字)——
三個錯誤共同的形狀都是「轉述當事實」。

**怎麼落地**:工單模板(`.orca-brief/TASK.md.template`)已經把「工單本身可能是錯的」列成固定
段落,這條是協調者對自己的補充規則:寫工單、傳訊息時,任何轉述的技術前提後面明寫「【推】,
你實測」;唯一的例外是協調者自己剛重跑過指令、貼得出原始輸出的時候,才可以標【驗】。
**這條規則不能只寫給 worker**——工單模板是寫給 worker 看的,但轉述當事實的錯誤,協調者自己
犯得比 worker 更頻繁。

**刻意不遵守的專案**:無。

**擴寫(專案 A 協調者第四次踩到後)**:預設【推】的範圍是「協調者轉述的一切」,**不分來源**——技術顧問的話、worker 的回報、上一輪的 `.orca-brief/REVIEW.md`、自己三小時前寫的筆記,都一樣;規則從「對誰」改成「對什麼」。實例:協調者從上一輪 worker 的 grep 回報抄「壞檔噴 stack 卻 exit 0」進工單,實測是另一個更嚴重的洞(P-50)。

**實例**:協調者與技術顧問都推測「六份 standalone 回歸內容不同」,worker 實測證明六份跑的是同一個 subprocess,然後找到比 allowlist 更好的解(一份共用場景掛六個 `@iN`)。**兩個人的推測一致並不會讓它變成事實。**

### (m) 審核輪要多驗幾個作者沒提到的形狀

**做法**:審核工單除了列出的驗收條件,固定加一句:「除了上面列的,自己想幾個工單 / commit
message 沒提到的形狀去試」。

**為什麼**:只驗證作者(開發者或工單撰寫人)想得到的案例,等於讓作者自己出考卷——作者的
思考範圍本身就是漏洞最容易躲藏的地方,審核如果只覆核清單,永遠測不到清單外的東西。

**證據**:PITFALLS P-28 的審核 agent 除了工單列出的案例,額外多試了 11 種巢狀圍欄變體
(四反引號、未閉合、inline code 裡的 `](`、`~~~`),全部正確——這 11 種沒有一種在原本的清單裡,
純粹是審核者自己多想的。

**怎麼落地**:審核類工單(或 `phase-acceptance` 的審核步驟)固定要求審核者交回報告時,附至少
幾個「自己想的、不在清單上」的輸入形狀與結果,不是只覆核工單列出的項目。

**刻意不遵守的專案**:無;C 的定向反向驗證(見 (e))補了一種機械化的替代品,但即使有反向驗證,
審核仍建議多試幾個未列出的形狀,兩者互補,不互斥。

### (n) 協調者出錯時明說「我工單寫錯了,照你實測的」

**做法**:worker 的實測結果跟協調者工單的內容衝突時,協調者回覆的第一句固定是「你對,我工單
寫的錯了」,然後才講怎麼繼續——不含糊帶過,不先論證工單哪裡「其實也對」。

**為什麼**:worker 要能相信「自己實測到的現實」勝過「工單寫的」,而這需要協調者明確、反覆地
授權;含糊帶過一次,worker 下次遇到類似衝突可能會選擇照工單做而不是照實測做,因為它不確定
「頂撞工單」是不是安全的。

**證據**:A 協調者一張工單寫錯兩個基準數字(重複率、圖形狀),worker 兩次都用實測結果推翻;
協調者自己的記錄寫:「如果第一次含糊帶過,第二次它可能就照工單寫了」。

**怎麼落地**:沒有獨立的檔案機制,是協調者的行為規則,寫進 `CLAUDE.md` 或 autopilot 的角色
說明裡:worker 回報與工單前提衝突,協調者的第一句話明確認錯再往下走,不是重新論證工單對不對。

**刻意不遵守的專案**:無。

### (o) ADR 由做的人寫、審核的人重算數字

**做法**:ADR(或 `.orca-brief/REVIEW.md` 裡的決策段落)由**實際做那件事的人**寫,不是協調者事後轉述;
審核輪的責任是重算 ADR 裡出現的每一個數字,對不上就是編的,退回去改。

**為什麼**:ADR 的價值在細節與數字,而那些只在剛做完的人腦子裡最新——協調者事後轉述,容易
寫成一段空泛的「我們決定用 A」,漏掉真正有用的細節。但做的人寫的數字也可能編(壓力下湊一個
看起來合理的數字),所以要配「審核輪重算」當配套,不是單靠「誰寫」解決問題。

**證據**:PITFALLS P-15 記錄的 ADR-043,兩個數字(72 對 34)經審核輪重算後其實是 75 對 33——
如果 ADR 由協調者事後轉述,審核輪也照抄舊數字,這個編造永遠不會被抓到。

**怎麼落地**:`/decide` 留給協調者自己做的派工 / 合併順序類決定;技術取捨類的 ADR,內容由做
那件事的 worker 或審核 agent 在自己的工單 / `.orca-brief/REVIEW.md` 裡先寫,協調者統一編號、收進
`02-decision-map.md`,但**不改內容裡的數字**——數字有問題退回去讓原作者或審核輪重算,不是
協調者代改。

**刻意不遵守的專案**:A 尚未把這條寫成強制流程(目前是協調者自己選擇性採用),B、C 暫時仍是
「誰在場誰寫」,沒有明確的分工规则。

## (p) 覆核一個測試修正時的三步

**做法**:覆核「把一條紅測試改綠」這種修正時,固定跑三步,不是看一眼 diff 就過:

1. **反向驗證**:把舊值放回去,確認**剛好是宣稱的那幾條**測試變紅——不多不少。
2. **確認規則還被守著**:那條改動的測試原本要防的規則,拿掉之後用**兩種不同方式**弄壞實作,
   確認還有其他測試會紅;兩種都不紅,代表規則其實沒有測試在守。
3. **普查同一個常數 / 模式的每一處用法**,列出每一處「算不算數」以及為什麼——不是只看
   自己動到的那幾行。

**為什麼**:測試修正最容易犯的錯不是「改錯了」,是「改對了眼前這條,但沒發現同一個常數還有
別的地方在用,而那些地方沒有被普查過」——第一步只驗證「我改的這條」,第二步只驗證「規則還在」,
兩者都驗不到「還有沒有其他地方也踩到同一個坑」。

**證據**:PITFALLS P-53,一個寫死的時間常數(`T0`)在 39 處被使用,實際跟「日期依賴測試」這個
坑有關的只有 2 處——覆核者如果只看那條被改的測試,不會發現另外 37 處其實安全,也不會發現
如果普查不完整,可能漏掉真正還有問題的那一處。「今天剛好只有兩條紅不代表只有兩條有病」。

**怎麼落地**:審核類工單(或 `phase-acceptance` 的審核步驟)遇到「測試修正」這個類別時,固定要求
附上三步的紀錄,不是只附「改前改後 diff」。

**刻意不遵守的專案**:無。

## (q) 對帳比 multiset 不比 count

**做法**:兩份測試結果要對帳「是不是同一組測試」時,比對 **multiset**(每個測試名稱各出現幾次,
或用 classname+name 完整限定名),不比較**總數**;比對 multiset 時也不能用 `set(names)`——
重複名稱會被集合悄悄吃掉。

**為什麼**:總數是一個聚合值,不同的組成可以加總出同一個數字,對帳只看總數等於默認「總數相等
就代表內容相同」,而這個默認本身沒有被驗證過。用 `set()` 比對還有第二層問題:去重本身就是一種
資訊損失,兩個 testcase 同名不代表它們是同一條(不同檔案、不同 suite 都可能同名)。

**證據**:合併對帳時兩棵樹都算出總數 8044(分支 8036+4+4,main 8036+8),數字一模一樣,但
實際上少了 4 筆測試——「數字對得上,內容少了 4 筆」。同一個 repo 另外實測:1691 個 testcase
只有 1683 個不重複名稱,8 個同名,若用 `set(names)` 比對會**憑空少算 8 筆**,而且這個「少算」
本身還會呈現出一個看起來乾淨、實則錯誤的結果。

**怎麼落地**:合併後保留 junit 報告(`reports/junit/<sha>.xml`),下次合併前用**名稱 + 出現次數**
(或 classname+name 完整限定)跟上一份基準做 diff;`autopilot` §2 的合併流程已經把這條寫進收割步驟。

**刻意不遵守的專案**:無。

**修正(來源 nightmare-assault,2026-09-05)**:棘輪類的綠基準要**釘住產生它的 base commit hash**,
不要釘 `main` 這種會一直往前跑的活動分支——`main` 不是一個固定點,拿它當基準等於基準本身也在悄悄漂移。
**基準檔名要帶 hash,不要帶遞增數字**:`baseline-8064.xml` 這種以序號命名的檔案是 P-59(寫死了會過期
的識別子)的變體——序號本身不攜帶「這是對著哪個 commit 量的」這個資訊,下一次合併後序號要不要進位、
進位到多少純靠人工判斷,判斷得到但沒人保證判斷得對。本模板的 `reports/junit/<sha>.xml` 已經是這個形狀,
這裡把它寫成明確規則,不只是實作細節。

## (r) 退化路徑見證器的報告格式:三個只降不升的桶

**做法**:(f) 節說的見證器機制落地時,報告固定分成三個桶,各自只能**降**,不能升:

1. **未聲明**(swallow / default-path 之類的退化訊號,測試走過了但沒有明確標記 `allow_degraded`)
2. **從未執行**(某個退化訊號被埋在程式碼裡,但目前**沒有任何一個測試**走到它——比「未聲明」更嚴重,
   代表這個訊號完全沒被觀測過,不知道它在正常路徑還是退化路徑上)
3. **跨擁有者**(退化訊號所在的模組跟走到它的測試分屬不同擁有者——通常代表這是一個共用元件的
   fallback,沒有單一owner 對它的退化行為負責)

**優先順序**:三桶都要求「只降不升」,但**「從未執行」優先降到 0**——這個桶代表完全沒被觀測過的
盲區,風險比「已知但沒標記」高一個等級。

**為什麼**:todo 式的單一數字(例如「N 個退化訊號」)會把三種完全不同性質的問題混在一起,看不出
該優先處理哪個;拆成三桶讓「這個數字為什麼升了/降了」有明確的歸因。

**證據(專案 A 基準,ADR-044)**:152/1779 個 vitest 測試走了沒有 `allow_degraded` 標記的退化分支
(未聲明桶 101 個是 swallow 類、74 個是 default-path 類,兩者有重疊所以合計不是簡單相加),跨擁有者
13 個,從未執行 2 個;見證器模組放在 `packages/contracts/observe`(不是放進某個功能資料夾底下)——
理由記在 `owners.json` 與對應的 ADR 裡:這是**觀測基礎設施**,不是契約,不受硬規則保護,但也不屬於
任何單一功能,放共用的 `contracts/` 底下比放進某個 `features/NN-x/` 更準確。

**怎麼落地**:
1. 先跑報告模式(見 (f) 節),把現有的退化訊號跑出三桶的初始基準數字,committed 進 repo。
2. `check:known-defects` 一類的 gate 邏輯加一個「棘輪」比對:任一桶的數字比基準高 → FAIL;
   降低基準是獨立 commit,不跟功能改動混在一起(同 (b) 節撥高棘輪基準的規則,方向相反)。
3. 「從未執行」桶的每一筆,先寫一個能命中它的測試(哪怕只是驗證「這個分支會被走到」),再考慮
   要不要幫它補 `allow_degraded` 標記。
4. `@manual` / `@e2e` 確認前,先看這份報告——見 (f) 節。

**起源**:nightmare-assault 一天內抓到 35 個測試檔在 fallback 分支上綠了兩週沒人發現,是這整個機制
(包含 (f) 與這一節)存在的理由。

**刻意不遵守的專案**:A、B 尚未把見證器機制上線到自己的產品程式碼(A 目前只有基準數字與模組落點的
規劃,還沒有全面鋪 witness() 呼叫點)。

## (s) 棘輪基準的三道鎖

**做法**:任何「棘輪類」的基準檔(見 (b)、(r),以及涵蓋率 / 已知缺陷這類只准往好的方向變的量),
落地時要有三道鎖,不是只靠「數字只能降」這一句口號:

1. **不在基準裡的項目必須通過**——基準檔只登記「已知、暫時被允許」的例外,不在名單裡的東西沒有
   被允許,一律要求正常通過。
2. **在基準裡的項目必須仍然是失敗的**——如果一個「已知例外」的項目某天自己變成通過了,這是
   **FAIL**,而且訊息要求「把它從基準裡移除」,不能默默讓它繼續待在基準裡(基準裡多留一個
   其實已經修好的項目,會讓人以為它還沒修好,也會讓基準的數字比實際情況難看)。
3. **條數只准減少,而且要有一個寫死的上限**(`max`)當防線——條數增加代表有新的例外被悄悄加了
   進來卻沒人審查,寫死的 `max` 讓「增加」這件事在設定檔的 diff 裡看得到,不是一個隱性規則。

**為什麼**:光說「棘輪只能往好的方向變」沒有講清楚三種情境各自要怎麼判——一個項目從「在基準裡」
變成「通過」看起來像進步,但如果沒有人把它從基準移除,基準本身就開始說謊(明明已經修好,報告卻
還在說它是已知例外);反過來,不在基準裡的項目开始失敗,也要能被抓到,不能因為它「不在清單裡」
就被放過。

**證據(專案 A,P-44 升類覆核,89 個探測目標)**:裸 stack trace 44 個、單看 exit code 21 個、
跟「健康」訊息同一份文案 14 個、跟「安靜」訊息同一份文案 5 個、沒指名具體路徑 5 個,合計 89——
覆核時發現舊版基準檔的比對只做了「條數不增加」這一道鎖,沒有另外兩道:結果一個已經修好的項目
被繼續算進基準(鎖 2 沒做到),另一個不在基準裡的新違規因為總數還在 `max` 以內而沒被攔下來
(鎖 1 沒做到,因為當時的比對只看總數不看逐項)。加齊三道鎖之後才真的抓到那兩處。

**刻意不遵守的專案**:無;B、C 尚未實戰過需要棘輪基準的場景。

## (t) 派工前先做衝突 grep

**做法**:開一張工單、把某個 phase 排進本週要做之前,先 `grep -rn <要改的名字> tests/ features/`
看有沒有別的地方已經在用同一個名字,並把工單的 AC 逐條跟目標 `FEATURE.md` 的「不在範圍」對過一次。

**為什麼**:NEXT.md 的 gate 只保證「依賴的 phase 已經 done」,不保證「這次要動的東西沒有跟別的

## (u) 掃描器不自我豁免,fixture 要拼得出真違規

**做法**:任何掃描類守門的**測試**,不能因為「這是守門自己的程式碼 / 設定」就被排除在掃描範圍外——
守門也是程式碼,跟被它掃的東西適用同一套規則。驗證守門的 fixture 要真的**拼得出**一個會被判定
違規的樣本,不是只驗證「乾淨的樣本會通過」;而且要**釘一條測試**專門驗證「fixture 仍然拼得出違規」
這件事本身——fixture 本身也會腐爛(掃描規則改了,舊的 fixture 可能不再觸發它原本該觸發的違規,
沒人發現)。

**為什麼**:掃描器最常見的自我豁免形狀是「這段是我自己的程式碼,不用被我自己掃」,這正是
P-33(守門對著代理指標而非不變量)的另一種變體——不變量是「這個掃描器該抓的東西,任何符合條件的
程式碼都逃不掉」,自我豁免直接違反這個不變量。

**證據**:專案 A commit a20091b,一個掃描器的測試套件原本假設「fixture 目錄本身不會被掃到」,
結果掃描規則後來改了(涵蓋範圍擴大),fixture 目錄裡刻意留的違規樣本因為在排除清單裡反而測不到
真違規,測試看起來全綠,實際上「fixture 拼得出違規」這件事早就不成立了。

**怎麼落地**:掃描器自己的原始碼、測試檔、設定檔要嘛乖乖被自己掃(掃到的話用正常的方式排除,
不特殊化),要嘛有明確理由記在 `owners.json` / `gates.config.json` 的例外清單裡(理由非空字串,
同 gherkin-dup 的 allowlist 規則);fixture 目錄額外釘一條測試:「拿現有 fixture 跑一次掃描器,
必須至少命中一個違規」,fixture 改動後這條測試要能繼續紅,紅不了就代表 fixture 已經不再代表
真違規,要修 fixture 不是放寬掃描規則。

**刻意不遵守的專案**:無。

**nightmare-assault 的做法**:當平行審核輪的負載達到某個門檻(他們的門檻是 ≥30)時,允許把兩張
獨立的合併請求併成一次跑,前提是同時滿足五個條件(不衝突的檔案範圍、兩者都已通過各自的完整檢查、

## (w) 嚴格級驗收:另一個 session、第一步固定突變、失敗訊息原文

**做法**:嚴格級模組的 `/phase-done` 整個流程由跟實作者不同的 session 執行(不是只有變異測試那一步
換人),而且這個 session 的**第一步**就是跑定向反向驗證或變異測試,不是照 `phase-acceptance` skill
原本的步驟順序(定位 → 前置檢查 → 自動場景 → … → 第六步才做變異)排到最後才做。通過的證據是
**炸掉那條斷言的失敗訊息原文**,逐字貼進驗收報告,不是「幾條測試變紅了」這種計數。

**為什麼**:如果測試本身沒有真的守住宣稱要守的行為,後面的單獨執行檢查、`@manual` 確認都是在
驗證一個地基不穩的東西;先確認地基,後面幾步不成立時可以直接省下去做的力氣。失敗訊息原文比
計數更難偽造——見 (h) 節的完整論證。

**證據**:AI_KM 用這個順序抓到過「宣稱通過但測試結構上不可能失敗」的個案(PITFALLS P-65),如果
還是照原本第六步才做變異的順序,前五步會先浪費時間在一個註定要被推翻的驗收上。

**怎麼落地**:已經寫進 `.claude/skills/phase-acceptance/SKILL.md` 第六步(變異測試)的段落。

**刻意不遵守的專案**:B、C 尚未把「換 session」這件事機制化(目前靠人工提醒),但兩者都已經採用
「失敗訊息原文當證據」這條(見 (h) 節)。

## (x) 守門要對著會變的量,不是對著結構的存在

**做法**:守門的斷言要對著一個**會隨程式碼變動而變化的量**(分數、順序、內容、身分、比對結果),
不是對著「這個東西存在」這種結構性事實——尤其是在**組合層**(把幾個模組串起來的那層):組合層
本身通常沒有自己的核心邏輯,守門容易寫成「這個函式被呼叫了」「這個物件有這個欄位」之類的存在性
斷言,而存在性斷言在組合邏輯本身壞掉之後往往仍然成立(函式還是被呼叫了,只是呼叫順序或參數錯了)。

**為什麼**:跟 (h) 節「反向驗證證據是失敗訊息原文」同一個道理的組合層變體——一個只驗證「有結果」
「沒拋錯」「這一步執行過」的守門,在組合邏輯真的壞掉時往往仍然通過。

**證據**:AI_KM ADR-0015 記錄的具體形狀:一個組合函式串了三個子模組,守門原本斷言「三個子模組都
被呼叫到」,但真正會壞的地方是**呼叫順序**(先驗證再寫入 vs 先寫入再驗證,語意完全不同)——三個
子模組確實都被呼叫了,守門因此一直是綠的,直到有人手動測試才發現順序錯了整整一個版本。

**怎麼落地**:寫組合層的守門前先問「如果這一層的邏輯真的壞了(順序錯、參數傳錯、條件分支走錯),
現在這條斷言會不會跟著變紅」,答不出來就代表斷言對的是存在性,不是會變的量,要重寫。

**刻意不遵守的專案**:無;A、C 尚未在組合層踩到過這個具體形狀,先把規則寫進來備用。

## (y) known-defect 的處置:逐份按證據等級裁,不一律追認或回退

**做法**:`@known-defect` 標記的場景需要被處置(修復、繼續延後、或撤銷標記)時,**逐份**依它的
證據等級判斷,不套用「所有已知缺陷一律追認繼續延後」或「所有已知缺陷一律要求立刻回退」這種一刀切
的規則。**特別是**:如果一個 `@known-defect` 鎖住的其實是**對某條無例外硬規則的違反**
(`hard_rule: true`),那份登記的 `fix_in` 不准是佔位值(`""` / `"未定"` / `"TBD"`)——一個
「之後再修」的標記不能拿來把硬規則的違規合法化,那跟「用一個 gate 例外代替真正修復」是同一族問題。

**為什麼**:已知缺陷登記表存在的目的是「讓紅色可以被看見、被追蹤」,不是「讓紅色變得可以被忽略」。
一刀切的處置規則(全部追認或全部回退)都會讓登記表失去它原本的功能——全部追認等於默許任何缺陷
都可以無限期延後;全部回退則失去了「暫時容忍已知的、非硬規則類缺陷」這個機制原本要解決的問題
(合併節奏被少數邊緣案例卡死)。

**證據**:nightmare-assault 的做法是每一筆登記表項目附上發現時的證據強度(重現步驟是否完整、
影響範圍是否清楚),審核時逐份核對證據等級再決定處置方式,而不是看登記表的「已知」二字就直接放行。

**怎麼落地**:`scripts/check-known-defects.ts` 的 `hard_rule` + `fix_in` 檢查是這條規則的機械層;
`.claude/skills/phase-acceptance/SKILL.md`「合併 ≠ done」一節已經把 `fix_in` 規則寫進去。人工判斷
的部分(要不要追認、要不要要求立刻修)留給技術顧問逐份裁,不寫死成自動規則。

**刻意不遵守的專案**:無。

## (z) 守衛條件不可用被測對象算出的值當條件

**做法**:測試裡任何形式的守衛——`if` 才斷言、`skip` 的判斷式、提早 `return`——它的條件本身**不准**
是從被測函式 / 被測物件算出來的值。守衛要嘛不設(直接斷言),要嘛用測試自己獨立建構、跟被測物件無關
的事實去決定(例如「我自己起了一個臨時 worktree,所以現在確實在 worktree 裡」,而不是「問被測函式
`isInWorktree()` 現在算不算」)。

**為什麼**:判準是「把被測函式改壞,那條斷言還會不會執行?」——如果守衛條件本身就是拿被測函式的輸出
去算的,被測函式一壞,壞掉的輸出有機會剛好讓守衛條件也跟著變得不成立,斷言直接被跳過,測試從頭到尾
沒有真的驗證任何東西,但看起來是綠燈。這是「陽性對照驗的其實是被測物存在,不是探針有沒有作用」
(PITFALLS P-68)的變體:P-68 是「探針送出去的東西不對」,這條是「決定要不要送探針的邏輯本身,問了
不該問的人」。

**證據**:`mutate.test.ts` 有一條斷言寫成 `const inWorktree = strykerLockPath() !== join(REPO_ROOT,
'.stryker.lock'); if (inWorktree) expect(seen).not.toBe(...)`——`strykerLockPath()` 正是這個測試要
驗證行為的那個函式。它真的壞掉(回傳了 worktree-local 路徑而不是預期的主 repo 路徑)時,`inWorktree`
判斷式的值也跟著變成 `false`,`expect` 那一行完全沒有機會執行,綠燈跟「真的驗過」無法區分。

**怎麼落地**:寫測試前先問「這個 if / skip 的條件是不是拿被測物件的輸出算的?」是的話換掉——用測試
自己造的固定狀態(臨時 repo、明確指定的 cwd、寫死的 fixture)取代;審核清單看到守衛式斷言(不是
單純的前置條件檢查,而是「符合某個條件才驗證核心行為」的那種)一律追問這個判準。

**刻意不遵守的專案**:無;這是覆核自己改壞的測試時發現的,尚未在其他兩個專案驗證過同型案例。

## (aa) 見證器第四桶:「刻意」登記表

**做法**:(r) 節的三桶(未聲明、從未執行、跨擁有者)之外,加第四桶「刻意」——一個測試如果
存在的目的就是為了驗證某個退化訊號才寫的(不是意外路過),登記進 `intended.json`,每一筆
`{ file, test, signal, reason, since }`。登記表本身要被驗證:每一條登記的 `test` 真的執行到
`signal`,否則 FAIL「登記表腐爛」(測試改名、刪掉、或不再走那條分支之後,登記表沒跟著更新)。

**準入判準**:問「這個測試存在的目的就是要走這條退化分支嗎?」,不是「它有沒有順便走到某條
退化分支」——後者屬於未聲明桶,不能因為「反正有走到」就升等成刻意。

**不做的兩件事**(刻意不做,不是漏做):不上調 (r) 節「未聲明」桶的基準——補完「從未執行」桶
之後把一條測試搬進刻意桶,未聲明的基準只能降,不能因為搬走一條就把基準往上調來配合;不另外做
一套「標記機制」(例如在被測程式碼裡加 `@intended` 之類的 annotation)——登記表本身就是唯一的
標記,標記寫在登記表側、不寫進被測程式碼側:寫進程式碼側的標記,程式碼改了容易忘記跟著改,
寫在獨立的登記表側,登記表的驗證(每條真的觸發)本身就會抓到「程式碼變了但沒人更新登記表」。

**為什麼**:補完「從未執行」桶的測試之後,如果直接把新測試算進「未聲明」桶,會讓「未聲明」的
數字必然上升——這違反 (r) 節「三桶只能降」的約定,逼團隊在「修從未執行」跟「不讓未聲明變難看」
之間二選一。第四桶把「這條就是刻意驗證退化路徑」的測試獨立出來,讓補測試這件事不會反過來讓
另一個指標變差。

**證據(專案 A)**:補完「從未執行」桶(30 → 0)之後,160 個測試被重新分類過,8 個進刻意桶,
未聲明桶維持 152(沒有因為補測試而上升,補之前之後都是 152/152),跨擁有者桶維持不變。

**反向驗證兩種**:(a) 把登記表裡某一條的 `test` 改名(測試檔案裡的函式名或描述跟著改),不改
登記表 → 應該 FAIL「登記表腐爛,`test` 找不到」。(b) 讓那條測試不再走註冊的 `signal`(例如把
它驗證的退化分支拿掉或改成正常路徑)→ 應該 FAIL「登記了但沒觸發」。兩種改回來 → 綠。

**刻意不遵守的專案**:B、C 尚未把見證器機制的三桶上線到自己的產品程式碼,第四桶自然也還沒有實戰。

## (ab) A3 第三例:兩人推論一致比一人講錯更危險

**做法**:【推】的判準是「這句話是怎麼來的」,不是「有幾個人同意」——兩個人各自獨立推論出
同一個結論,那個結論依然是【推】,不會因為兩個人都這樣想就升級成【驗】。

**為什麼**:「兩個人都同意」給人的心理感覺很像「這是事實」,連原本會提醒自己標記【推】的動機
都會消失(「這還要標嗎?我們兩個都這樣想」)——但兩個人一起推論出來的東西,查證成本並沒有比
一個人推論低,危險程度反而更高,因為它更容易被後面的人直接當事實往下傳。

**證據**:協調者與技術顧問都推測「六份 standalone 回歸內容不同,所以要用 allowlist 排除」,
worker 沒有照做,先實測發現六份跑的是同一個 subprocess,找到比 allowlist 更好的解(一份共用
場景掛六個 `@iN`)——兩個人的推測一致,並不會讓它變成事實。這是繼「一個人講錯」的兩個前例
(見 (l) 節)之後的第三例,形狀不同,值得單獨記。

**怎麼落地**:(l) 節「協調者轉述一律預設【推】」已經涵蓋「轉述」這個動作本身;這條補的是判準
本身的措辭:**標不標【推】,問的是「這句話是怎麼來的」(查過 = 事實,想出來的 = 推),不是
「有幾個人同意這句話」**——人數從來不是判準的一部分,只是常常被誤用成判準。

**刻意不遵守的專案**:無。

## (ac) 新規則第一次執行選無害場合

**做法**:一條新規則(新的守門、新的流程要求)第一次真的被拿來執行,刻意挑一個**後果無害**的
場合,不要被動等它自然發生在隨便哪個場合、剛好是高風險情境。

**為什麼**:規則第一次執行時,不確定是規則本身寫錯,還是這次狀況特殊。第一次執行剛好是高風險
場合的話,踩到問題要先花額外力氣釐清「這是規則的問題還是我這次真的特殊」;第一次執行是無害
場合,答案立刻清楚:規則有問題就直接修,不用擔心已經造成的傷害。

**怎麼落地**:新規則上線後,協調者/技術顧問主動找一個低風險的候選場合先跑一次。

**刻意不遵守的專案**:無;這是專案 A 協調者的做法紀錄,尚未在其餘專案驗證。

## (ad) worker 主動舉報自己最弱的一條要被肯定

**做法**:worker 交付時如果自己指出「我這條做得最弱、最不確定」,協調者/審核方要把這個舉報
當成加分,不是當成扣分退回。

**為什麼**:如果主動舉報弱點的下場跟被抓到弱點一樣(都被退回、都算沒做好),worker 下一次的
理性選擇是不舉報——弱點反而會拖到審核階段才被發現,審核成本更高、也更晚知道。**肯定舉報**
才會讓「講真話」變成對 worker 有利的選擇。

**怎麼落地**:回報格式(`.orca-brief/TASK.md.template`)已經有「我做的自主判斷」欄位;協調者
在回覆裡明確寫一句肯定的話,不要只用沉默帶過,也不要因為它自己講了弱點就多扣分。

**刻意不遵守的專案**:無。

## (ae) 注入物若不是斷言前提,註解明說它守什麼

**做法**:測試裡任何「刻意塞進去、但本身不是某條斷言直接前提」的東西(例如一個假的 prober、
一個看起來永遠不會被走到的分支守衛),旁邊一定要有註解寫清楚**它實際上在防什麼**,不要留給
讀者自己猜。

**為什麼**:這類注入物存在的唯一理由可能是「不要觸發某個訊號」——它本身不出現在任何
`expect(...)` 裡,單看程式碼結構,把它整個拿掉、翻掉,測試依然綠(例如被 `online=true` 這種
條件短路),看起來像一段可以安全砍掉的死碼,實際上砍掉會讓某個原本被壓住的訊號冒出來。沒有
註解,審核的人沒有辦法從程式碼本身看出這件事(`localProber` 就是這個形狀:它只為了不觸發
某個訊號而存在)。

**怎麼落地**:任何測試裡出現「這個東西看起來沒被斷言用到」的成分,寫測試的人自己先問一次
「這是不是純粹沒用到,可以刪?」——答案是「不是,它在守某個東西」,就地寫一行註解講清楚
守的是什麼,不要指望下一個看的人自己推理得出來。

**刻意不遵守的專案**:無。

## (af) 日期用 `date` 取,不要憑印象

**做法**:任何要寫進 ADR、CHANGELOG、PITFALLS 的日期,一律用 `date +%F`(或等價指令)實際
取得當下日期,不要憑印象或憑上一份文件抄的日期手寫。

**為什麼**:日期寫錯不會讓任何測試變紅、不會讓任何 gate 報錯——它是純粹的 metadata,錯了也
沒有任何機制會發現,直到很久之後有人想確認「這件事是什麼時候發生的」,才會發現對不上。這類
「沒有守門會管、但總有一天會被人依賴」的欄位,最值得養成「用指令取代記憶」的習慣。

**證據**:協調者自己在寫這批文件時把日期寫錯,沒有任何工具告警,是自己複查才發現——如果沒有
複查,這個錯誤要等半年後有人對時間線才會被抓到。

**怎麼落地**:寫入日期欄位前,先跑一次 `date +%F`,把輸出貼進去,不要用「今天大概是幾號」的
印象。

**刻意不遵守的專案**:無。

## (ag) 派工 checklist 補三條

**做法**:派工前(寫工單/交工單前)的檢查清單加三條:

1. 工單裡引用的每一個指令、檔案、gate,不能引用「將來才存在的東西」(見 PITFALLS P-79)——
   派工當下用 worker 實際要 checkout 的 base 驗證過真的存在。
2. 續用舊 worktree 時,看到紅燈之前先 `git merge main`(**不 rebase**)——分支落後 main
   太多,看到的紅可能是 main 早就修好、只是這個分支還沒跟上,不是這次改壞的。
3. 驗收條件訂出來之後自問:「**這個條件用廢話能不能滿足?**」(見 PITFALLS P-80)——能滿足
   就要換一個更貼近實質的判準。

**為什麼**:三條分屬三個不同時間點(派工前、worker 開工時、驗收條件訂定時)但同一類問題——
「檢查清單」本身容易漏掉不常想到的項目,把已經吃過虧的具體項目寫進固定清單,比指望每次都
想得到可靠。

**怎麼落地**:`.orca-brief/TASK.md.template` 與 autopilot §2 的派工流程各自把這三條加進去
(見本版 CHANGELOG)。

**刻意不遵守的專案**:無。

## 三個專案都刻意不遵守的範式條文

有三條範式本體的規則,三個專案**都**明確選擇不照做,而且都有記錄下來的理由——這不是散漫,
是規則跟現場條件對不上時,誠實地記一筆 ADR 而不是默默違反。既然三個專案的意見一致,
範式本體照這三條的方向調整,而不是繼續要求「照做但三個都不做」。

### WIP ≤ 2 → 改成「同開上限 = ready 集合大小」

**原規則**:同時 `in-progress` 的 phase 建議不超過 2 個。

**三個專案的做法**:C 是「能開多少開多少」——ready 的 phase 全部同時派出去;B 一開始遵守,
回填階段 11 個資料夾同時開工(零重疊,因為回填的場景各自綁到不同的既有測試入口),記了一筆
ADR 之後之後長期維持 WIP 4。兩者都不是隨意打破,是**認為 WIP 上限的真正目的(避免互踩、
避免合併衝突)在滿足特定前提時可以用別的方式達成**。

**調整後的條文**:**同時開工上限 = 目前 ready 集合的大小**(ready 多少個就可以開多少個),
代價由另外兩條規則吸收,不是不設限制:
- **一次合一條**:合併回 main 一次只處理一個 phase 的分支,不批次合併——避免多個平行分支的
  衝突同時浮現,把「多開」的複雜度移到合併節奏上而不是開工節奏上。
- **rebase 由協調者吸收**:worker 的分支落後 main 時,rebase 這件事由協調者做,不要求每個
  worker 自己處理落後與衝突——worker 只管自己的 phase,協調者管彼此之間的干擾。
- **審核輪 ≤ 1**(P-34 的教訓):即使開工上限提高,同時處於「跑變異測試」這種吃重審核動作的
  worktree 仍然限制在 1 個,避免互相 OOM。

這條調整記為 P-34 之後的範式規則(見 `autopilot` §2.3)。

### stryker 變異分數 → 與定向反向驗證二選一

**原規則**:嚴格級模組的變異測試分數是硬門檻。

**三個專案的做法**:B 的理由是「機器弱」——跑 Stryker 全套變異測試的算力成本在他們的環境下
高到不成比例,改用定向的 `mutate.mjs`:一次一個突變、一個明確的斷言,直接驗證「這行程式碼
被這條測試守住」,不需要跑完整套變異分析。C 走的是同樣方向的 Python 版 `mutate.py`(見 (e))。

**調整後的條文**:嚴格級模組的驗收,**變異分數(≥ 目標門檻)與定向反向驗證(對照表逐列重跑必紅)
二選一皆可,但嚴格級至少要有一種**——不能兩者都不做。標準級沒有這個要求,維持「跑了未達標
只回報不擋」。這條已經寫進本模板 1.3.0 的 `phase-acceptance` skill 第六步。

### sprint 檔與 `/sprint` → 改成選配,autopilot 回報是預設

**原規則**:一週一次 `/sprint` 規劃,寫進 sprint 檔,週五回顧。

**三個專案的做法**:B 用 `autopilot` 每輪的固定回報格式取代 sprint 檔的角色——「這輪合併了什麼、
進行中什麼、卡住什麼」比一週一次的規劃更貼近平行開發實際的推進速度;retro(回顧)改成在
每個整合點做一次,而不是每週固定做。C 的做法一致:協調者觸發、每輪回報取代了 sprint 檔的
進度追蹤功能,keep-working 迴圈本身就是持續在規劃「下一個 ready 的是什麼」。

**調整後的條文**:sprint 檔與 `/sprint` 改為**選配**——單人開發、或還沒有 autopilot 迴圈在跑的
專案仍然適用,照原本的節奏用;一旦 autopilot 開始跑,**每輪回報取代 sprint 檔成為預設的進度
追蹤方式**,retro 挪到整合點做。這條已經反映在 `docs/03-agile-workflow.md` 的「最小模式」段落
