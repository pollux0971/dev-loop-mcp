# Blast radius:這個改動會弄壞哪裡

改寫自 pstack 的 blast-radius(MIT,見 `docs/dlm/THIRD-PARTY.md`)。

列出誰呼叫了它不是重點,grep 一秒就有。重點是 grep 看不到的壞法,以及證明。

## 證明到哪一層

每個「安全是因為……」的說法,在便宜的範圍內往下推,並說停在哪一層:

1. 你說的。單獨一句不算數。
2. 指出那一行(`檔案:行`,或套件原始碼)。
3. 一步一步走過壞掉的情況,證明走不到。
4. 跑過:一支小 script 或測試呼叫真的程式,錯了會大聲失敗。
5. 在真的應用程式裡重現。

## 步驟

1. **看改動**:提案的 intent、owns、gherkin(`node tools/dlm.mjs show <節點或提案>`),或已經有的 diff。
   寫出它實際會改變的行為,包含 diff 沒寫明的部分。`docs/AS-IS.md` 的「已知的坑」先讀。
2. **找那一件事**:大多數看起來危險的改動,其實是因為某一件事而安全(例:「這個欄位只有匯出用到」)。找到它。
3. **看 grep 看不到的地方**:別的語言或程式讀同一份檔案或資料、設定或環境變數、資料格式(JSON 欄位、CSV 欄位順序)、
   執行時機(啟動時、結束時、非同步)、套件的實際版本。
4. **誠實評估**:每個風險寫發生機率與代價。確認過的留下;檢查過沒問題的另外列。
5. **證明那一件事**:寫一支 script 放在 `.dlm/intake/` 底下(不進主線),跑它,貼結果。
   證明不了就寫「未證明」。

## 回覆

- **它做了什麼**:包含不明顯的部分。
- **安全是因為**:那一件事、推到第幾層、證明的輸出。
- **風險**:每條寫怎麼壞、`檔案:行`、多可能、多嚴重、怎麼檢查。
- **檢查過沒問題的**:一行一條。
- **對提案的建議**:哪些既有檔要放進 `characterize.targets` 釘住行為、哪些行為要寫進 gherkin、owns 要不要加減檔。

這是建議,不是改動。要改提案,照 `intake` 做,使用者說好才批准。
